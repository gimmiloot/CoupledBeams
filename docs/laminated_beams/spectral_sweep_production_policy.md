# RLB-SWEEP-FAST: политика быстрого спектрального sweep

## Область применения

`RLB-SWEEP-FAST` задаёт общий численный порядок построения параметрических
спектров. Production-диапазон включает независимо упорядоченные позиции
1--8 и позицию 9 как guard root. Расширенный хвост до позиции 13 по умолчанию
не вычисляется.

Реализация `spectral-sweep-runner-v2` принимает одномерную конечную сетку
скалярного параметра. Значения параметра должны строго возрастать. Повтор,
обратный порядок или нечисловое значение отклоняются до вызова model callback.

Быстрый режим применяет продолжение спектра только для локализации интервалов
поиска. Прогноз не является частотой, не записывается вместо корня
характеристического определителя и не используется для сглаживания данных.
Номер независимо упорядоченной позиции служит только численным локатором. Он
не определяет `branch_id` и не устанавливает модальную преемственность.

Эта политика относится только к управляющему численному слою. Она не вводит
новую физическую модель и не является отдельным исследованием собственных форм.

## Замороженная физика и граница callback

Уравнения движения, характеристические определители, граничные условия,
координатные соглашения, физические параметры и критерии приёмки корней остаются
в существующих solver-модулях. В частности, runner не содержит формул моделей
Эйлера--Бернулли, Тимошенко или Reddy.

Связь с конкретной моделью выполняет callback вида

```text
boundary_diagnostics(parameter, spectral_parameter)
```

либо адаптер к эквивалентному существующему API. Callback предоставляет исходный
и масштабированный определители, `sigma_min`, `sigma_max`, граничную матрицу и
диагностику качества корня. Полный глобальный поиск, локальный поиск и исходный
уточнитель корня также передаются как внешние операции. Runner управляет их
порядком вызова, но не меняет математическое содержание.

## Три независимые фазы валидации

Валидация fast-режима разделяется на три фазы.

1. **Oracle.** Сначала независимо фиксируется результат полного seed-free
   поиска. Для доступных случаев читаются неизменённые результаты RLB-2B и
   RLB-2C. Новые полные поиски допускаются только в объявленных трудных точках.
   Для oracle сохраняются semantic hashes.
2. **Fast.** Затем выполняется быстрый поиск. Прогноз в точке использует только
   ранее принятые точки текущего sweep. Частоты oracle в этой точке не читаются
   и не применяются как seeds или границы интервалов.
3. **Comparison.** После фиксации fast inventory сопоставляются позиции 1--8 и
   root 9. Результат сравнения не передаётся обратно в поиск.

Такое разделение не позволяет использовать контрольные частоты для построения
проверяемого fast inventory.

## Anchor points

В anchor point выполняется существующий полный seed-free global scan без
изменения его сетки, детекторов, уточнителя и порогов. Обязательными anchors
являются:

- первая и последняя точки сетки;
- каждая десятая точка общей сетки;
- точка, следующая за точкой fallback;
- точка, отмеченная gap- или spike-аудитом;
- точка, в которой локальный поиск не дал ровно девять корней.

Для сетки `beta = 0, 1, ..., 90 deg` базовый набор содержит
`0, 10, ..., 90 deg`. Для сетки `mu` с шагом `0.02` используется каждая пятая
точка, то есть базовый интервал между anchors равен приблизительно `0.10`.
Более частые anchors разрешены только после заранее заданного диагностического
события.

## Прогноз и локальные интервалы

Для первой точки после anchor применяется постоянный прогноз

```text
omega_hat_k(p_j) = omega_k(p_{j-1}).
```

При наличии двух предыдущих точек применяется секущий прогноз

```text
omega_hat_k(p_j) = omega_k(p_{j-1})
                 + (p_j - p_{j-1}) / (p_{j-1} - p_{j-2})
                 * (omega_k(p_{j-1}) - omega_k(p_{j-2})).
```

Прогноз сохраняет порядок ранее принятых независимо упорядоченных позиций.
Если соседние секущие прогнозы меняют порядок, эти позиции проверяются совместно
в одном multi-root locator interval. Это не задаёт modal identity: после поиска
корни снова независимо сортируются, а прогноз используется только для оценки
локального окна.

Для каждой одиночной позиции или заранее выделенной группы близких корней
сначала строится primary safety window. Его полуширина определяется
зафиксированными минимальным, относительным и motion-based запасами. Соседние
прогнозы задают midpoint partition, внутри которого остаётся primary interval.
Если predictor safety windows соседних позиций пересекаются, их связная группа
проверяется в одном multi-root locator interval. Это объединение относится
только к области локального поиска: частоты не усредняются и не сливаются,
callback обязан вернуть точное число отдельных корней, а проверки кратности,
дубликатов, residuals и фактического spectral gap сохраняются. После такого
группирования primary intervals должны быть непересекающимися; иначе выполняется
полный поиск.

Исторические программные поля `SearchInterval.is_cluster` и
`cluster_intervals` считают такие multi-root locator groups. Они не являются
доказательством физической кратности или cluster: физическая топология берётся
только из `RootRecord.multiplicity`, `nullity` и `cluster_id` исходного solver.

Verification interval строится независимым расширением primary interval.
Расширение не изменяет найденный корень и не используется как его оценка. До
вызова verification callback расширение ограничивается midpoint partitions между
locator groups и проверяется взаимное непересечение всех расширенных интервалов.
Пересечение также вызывает полный поиск.

В каждом допустимом интервале выполняются две независимые локальные операции:

1. primary-поиск sign-changing bracket с одновременным контролем локального
   минимума `sigma_min / sigma_max`;
2. verification-поиск в немного расширенном интервале либо с независимым
   determinant/sigma detector.

Обе операции используют исходный root refiner. Их результаты должны совпасть
с относительной точностью `1e-9` для позиций 1--8 и root 9. После уточнения все
корни сортируются заново.

## Приёмка корня

Fast-режим применяет только замороженные критерии полного solver. Для каждого
принятого корня проверяются:

- положительность и конечность частоты.

- determinant- и SVD-свидетельства корня согласно исходной политике.

- замороженный порог `sigma_min / sigma_max`.

- замороженный порог граничного null residual.

- отсутствие rejected status.

- отсутствие повторного учёта одного и того же корня.

- неубывающий порядок принятого inventory. Совпадающие численные значения
  допустимы только при явно подтверждённой кратности и согласованной cluster
  diagnostics.

Близость двух частот сама по себе не является основанием для их объединения.
Локальный sigma-only кандидат, включая возможный корень чётной кратности,
переводит точку на полный поиск. После fallback действует решение исходного
полного solver и его неизменные критерии.

## Автоматический fallback

Результат локального поиска полностью отбрасывается и заменяется результатом
полного global scan, если выполняется хотя бы одно условие:

- получено не ровно девять корней или отсутствует root 9.

- какой-либо residual не проходит замороженный порог.

- сгруппированные primary intervals или расширенные verification intervals
  пересеклись.

- корень вышел за свой safety interval.

- соседний spectral gap меньше заранее зафиксированного gap threshold.

- обнаружен возможный even-multiplicity или sigma-only root.

- determinant- и sigma-detectors не согласуются.

- отличие от прогноза превышает frozen locator threshold.

- primary- и verification-уточнения расходятся более чем на `1e-9`.

- точка отмечена post-sweep spike audit.

Сама точка fallback получает результат полного поиска и является anchor.
Следующая за ней точка также принудительно становится anchor. Причина, локальный
кандидат и принятый результат полного поиска сохраняются раздельно.

## Близкие корни и clusters

При малом соседнем gap выполняется локальный multi-minimum scan. Каждый корень
должен иметь отдельный bracket или отдельный минимум и собственную диагностику.
При неоднозначности используется полный global scan.

Runner сохраняет gap, cluster и nullity diagnostics, предоставленные solver.
Два близких корня не сливаются только из-за малого расстояния. Проверка
дубликатов удаляет лишь повторное представление одного корня в соответствии с
замороженной duplicate policy.

## Защита от изолированных всплесков

После sweep для каждой позиции и каждой внутренней точки вычисляется остаток
локального линейного прогноза по двум соседним точкам. Нормировка, абсолютный
floor и robust threshold фиксируются в manifest до расчёта. Критерий только
помечает изолированную точку как `SUSPICIOUS`; он не меняет частоту.

Для каждой такой точки полный поиск выполняется во всей тройке
`p_{j-1}, p_j, p_{j+1}`. Сначала рассчитываются все три inventory. Затем каждый
из них проверяется по тем же frozen root-quality и global-completeness gates,
что и обычный полный поиск. Частичный результат тройного аудита не принимается.
Допустимы три исхода:

- `REPRODUCED_BY_FULL_SCAN`: полный поиск воспроизвёл особенность. Значения
  сохраняются без изменения.

- `FAST_LOCATOR_CORRECTED`: хотя бы один fast inventory в проверяемой тройке не
  совпал с полным. Только для таких параметрических точек записываются результаты
  полного поиска. Исходные fast-значения и все замены сохраняются в audit CSV.

- `UNRESOLVED`: один из трёх полных inventory не прошёл проверку либо полный
  поиск не подтвердил ни fast-значение, ни воспроизводимую спектральную
  особенность. Точка остаётся явно квалифицированной и не скрывается.

Spline smoothing, moving average, удаление точки, усреднение соседей и ручная
правка CSV запрещены. Воспроизведённая особенность может соответствовать
кривизне спектра, пересечению или смене независимо упорядоченных позиций. Без
анализа собственных форм она не трактуется как смена модальной ветви.

## Preflight, время и память

Режим `--preflight` рассчитывает начало, середину и конец сетки, а также одну
заранее объявленную трудную точку. Для каждой точки сохраняются wall time,
peak RSS, число вычислений определителя, полных поисков, локальных уточнений и
матричных экспонент. По этим данным оцениваются полное время и peak RAM.

Целевой бюджет двух графиков равен 30 минутам. Если прогноз превышает 60 минут,
production sweep не запускается; сначала формируется profiling report.
Прогноз fast runtime считается допустимым только если representative
цепочка фактически выполнила хотя бы один primary и verification `FAST_LOCAL`
поиск. Подмена всех local-точек frozen oracle/full fallback не является
измерением fast-производительности и блокирует production-допуск.

Ускорение определяют как отношение wall time сопоставимого полного workflow к
wall time fast workflow. Обе величины должны относиться к одной сетке, модели,
аппаратной среде и thread policy. Измеренное ускорение отделяется в отчёте от
оценки, полученной экстраполяцией preflight.

Расчёт выполняется одним Python worker. Перед запуском устанавливаются

```text
OMP_NUM_THREADS=1
MKL_NUM_THREADS=1
OPENBLAS_NUM_THREADS=1
NUMEXPR_NUM_THREADS=1
```

Multiprocessing по умолчанию запрещён. Point-local arrays освобождаются после
записи точки. Неограниченные caches не допускаются.

Для beta-sweep разрешён bounded exact cache arm endpoint или transfer data,
если эти данные действительно не зависят от `beta` и оптимизация не требует
изменения physics module. Cached и uncached значения должны совпадать с
относительной точностью не хуже `1e-13`. При невыполнении этого условия cache
отключается; fast continuation остаётся основной оптимизацией.

Ключ cache используется без округления спектрального параметра. Размер cache
одновременно ограничен числом записей и оценкой числа байтов. Диагностика
сохраняет `entries`, `current_bytes`, `peak_entries`, `peak_bytes`, `hits`,
`misses`, `evictions` и `hit_rate`. Поэтому повторное использование данных
остаётся контролируемым по памяти и не объединяет соседние значения частоты.

## Транзакции, checkpoint и возобновление

Каждая параметрическая точка образует отдельную транзакцию:

1. расчёт;
2. проверка позиций 1--8 и root 9;
3. запись temporary file;
4. atomic rename или merge;
5. обновление checkpoint manifest.

Checkpoint содержит поля `completed_points`, `missing_points`, `failed_points`,
`qualified_points`, `last_completed_parameter`, `elapsed_time`,
`estimated_remaining_time`, `full_scan_count`, `fallback_count` и
`spike_audit_count`. Он также хранит fingerprint сетки, numerical settings,
callback contract и замороженных порогов. Несовпадающий fingerprint запрещает
тихое продолжение расчёта. Перед чтением point transactions runner сопоставляет
`sweep_id`, `model_id` и fingerprint с checkpoint manifest. Несовпадение
останавливает режим возобновления до вызова численных callbacks.

При `--resume` или `--missing-only` runner восстанавливает не только принятые
точки, но и причинное состояние anchor schedule. Если загруженная точка имеет
origin `GLOBAL_FALLBACK`, следующая незавершённая точка снова назначается
принудительным anchor. Поэтому прерывание процесса не отменяет требование
полного поиска после fallback.

Ошибка полного поиска в scheduled anchor или при fallback не создаёт принятую
point transaction. Перед повторной передачей исключения runner атомарно
обновляет checkpoint manifest и включает параметр в `failed_points`. Уже
записанные точки при этом сохраняются без изменения.

Режимы runner имеют следующий смысл:

- `--run` начинает расчёт по утверждённому contract только после завершённой
  fast/full validation. До допуска проверяются версия алгоритма, статус
  `OVERALL: PASS`, разрешённая итоговая формулировка, наличие non-anchor
  `FAST_LOCAL` evidence и сохранность хэшей physics и validation dependencies.

- `--resume` читает checkpoint и не пересчитывает завершённые точки.

- `--missing-only` вычисляет только отсутствующие или повреждённые точки.

- `--plot-only` не вызывает determinant callback и использует только проверенные
  сохранённые данные.

- `--validate-fast-vs-full` выполняет фиксированный контроль fast/oracle.

- `--preflight` оценивает ресурсы без запуска полного production sweep.

## Фиксированная валидация

Для beta-sweep проверяются точки

```text
0, 45, 54, 90 deg.
```

Для mu-sweep проверяются точки, зависящие от модели:

```text
EB:                         0.00, 0.80;
old Timoshenko, weak RLB:  0.00, 0.40, 0.60, 0.78, 0.80.
```

Это ровно 24 validation jobs. Полная сторона преимущественно читается из
immutable CSV с зафиксированным SHA-256; старые validation shards сохраняются
только как legacy evidence и не конвертируются в доказательство текущего v2.
Fresh full scan разрешён только при отсутствии reference или подтверждённом
fast/reference disagreement; суммарно допускается не более трёх таких scans.

Для каждой применимой модели сравниваются позиции 1--8 и root 9. Требуются
одинаковое число корней, сохранение отдельных членов close pair, одинаковая
cluster multiplicity, совпадение частот или cluster centre с относительной
точностью `1e-8`, одинаковая позиция guard root и прохождение всех замороженных
residual gates. Внутренняя local primary/verification проверка runner остаётся
более строгой: `1e-9`. Несогласованность строго выше root 9 в этот gate не
входит.

Spike protection подтверждается targeted tests, трудной точкой `beta=54 deg`
и обязательным full fallback для любой production-точки, которую post-sweep
audit отметил как suspicious. Сглаживание и интерполяционная замена корней
запрещены.

Если хотя бы одна обязательная точка не проходит эти условия, fast production
mode не разрешается. Порог не ослабляется; причина фиксируется отдельно.

Production-режимы не используют наличие неполного или устаревшего validation
каталога как неявное разрешение. `--run`, `--resume`, `--missing-only` и
`--plot-only` требуют целостный validation manifest действующей версии. После
валидации повторно проверяются хэши production physics и validation adapters.

## Выходные данные

Validation workflow сохраняет данные в
`results/laminated_beams/spectral_sweep_runner_validation/`. Минимальный набор
включает:

- `preflight_report.json`;
- `fast_vs_full_comparison.csv`;
- `anchor_checks.csv`;
- `fallback_checks.csv`;
- `spike_audit.csv`;
- `runtime_profile.csv`;
- `memory_profile.csv`;
- `report.md`;
- `run_manifest.json`.

Figures на инфраструктурном этапе не создаются.

## Статусы и условие допуска

После расчётов применяются статусы:

- `SWEEP-FAST-ROOT-ACCURACY: PASS / FAIL`;
- `SWEEP-FAST-ROOT9-COMPLETENESS: PASS / FAIL`;
- `SWEEP-FAST-SPIKE-PROTECTION: PASS / PARTIAL_PASS / FAIL`;
- `SWEEP-FAST-RESUME: PASS / FAIL`;
- `SWEEP-FAST-PERFORMANCE: PASS / PARTIAL_PASS / FAIL`.

`OVERALL: PASS` допустим только при `PASS` для точности корней, root 9, защиты
от всплесков и resume. Статус performance должен быть не хуже `PARTIAL_PASS` с
документированной причиной. Только после этого разрешена формулировка

```text
FAST_PRODUCTION_SWEEP_VALIDATED_FOR_FIRST8_PLUS_ROOT9
```

Настоящий документ задаёт критерии, но не присваивает перечисленные статусы.

## Ограничения

Политика не изменяет физические solver-модули и не сертифицирует произвольную
модель или параметрическую область. Она не выполняет branch tracking, MAC,
Ritz-, FEM- или отдельный root-13 audit в каждой точке. Продолжение не заменяет
полный solver: оно сокращает область локального поиска и при диагностическом
сомнении уступает место полному seed-free scan.
